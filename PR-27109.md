# CUDA: fast quantized-KV → f16 conversion for flash-attention on Ampere (fixes #27109)

## Problem

On Ampere GPUs (e.g. RTX 3090, cc 8.6), **prefill with a quantized KV cache + flash
attention collapses**, while generation is unaffected:

| KV cache | prefill (Qwen3.8-27B, 2×RTX 3090, ctx 65536, ubatch 2048, `-fa`) |
|----------|------|
| q8_0     | ~1000 t/s |
| q4_0     | ~74 t/s (GPU util 0–6%) |
| q5_1     | ~125 t/s |

This matches the reports in #27109. GPU utilisation sits at 0–6% during the slow
prefills, i.e. the GPU is stalled, not compute-bound.

## Root cause

On Ampere, prefill selects the **MMA-f16** flash-attention kernel
(`ggml_cuda_get_best_fattn_kernel` → `BEST_FATTN_KERNEL_MMA_F16`), which needs f16
K/V. So on **every** flash-attention call the whole KV cache is dequantized to f16:

```
// fattn-common.cuh
to_fp16_cuda_t to_fp16 = ggml_get_to_fp16_cuda(K->type);
to_fp16(K_data, K_f16, ggml_nelements(K), main_stream);   // whole KV → f16
```

Over a prefill this conversion is O(n²) in the KV length, so its per-element cost
dominates.

In `convert.cu`, `ggml_get_to_fp16_cuda` gives **q8_0** a dedicated half2-optimized
kernel (`dequantize_block_q8_0_f16_cuda`, guarded by `fp16_available`), but
**q4_0/q4_1/q5_0/q5_1 fall back to the generic element-wise dequant**. That generic
path is the bottleneck for the hot per-call KV→f16 conversion → quantized-KV prefill
stalls on Ampere.

## Fix

Add dedicated half2-vectorized `*_f16` conversion kernels for q4_0/q4_1/q5_0/q5_1
(identical dequant math to the reference `dequantize_q*`, `il/ir` tiling like
`dequantize_block_q4_0`, half2 stores) and dispatch to them under `fp16_available`,
mirroring the existing q8_0 case.

## Results (verified)

Qwen3.8-27B, 2×RTX 3090, ctx 65536, ubatch 2048, `-fa`, K==V type. All numerically
correct (`17*23 = 391`):

| KV type | before | after |
|---------|--------|-------|
| q4_0    | 74     | **1063** |
| q4_1    | ~157   | **825**  |
| q5_0    | slow   | **830**  |
| q5_1    | 125    | **824**  |
| q8_0    | 1002   | 1002 (unchanged) |

GPU utilisation goes from 0–6% (stalled) to ~100%. The remaining gap vs q8_0
(~825 vs ~1000) is expected: q4/q5 do extra per-element work (nibble unpack, and for
q5 the 5th bit from `qh`), and these kernels are a straightforward first pass (256
elems/block, no shared-memory staging) whereas the q8_0 kernel is hand-tuned
(shared-mem staged, 2048 elems/block).

## Note on q4_1/q5_0/q5_1

`ggml_cuda_fattn_kv_type_supported` (`fattn.cu`) returns `false` for q4_1/q5_0/q5_1
unless `GGML_CUDA_FA_ALL_QUANTS` is defined, so in a default build they never reach the
fattn path at all (they silently fall back to non-FA). The kernels above cover them,
but they only take effect with `-DGGML_CUDA_FA_ALL_QUANTS=ON`. **q4_0 and q8_0 are
FA-enabled in a default build**, so the common/important case (q4_0 — the smallest
FA-enabled quantized KV type) is fixed without any extra build flag.

## Build / test

CUDA 13.3, MSVC 2022, Ninja, `-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=86`
(add `-DGGML_CUDA_FA_ALL_QUANTS=ON` to also enable q4_1/q5_0/q5_1). Verified on
2×RTX 3090.
